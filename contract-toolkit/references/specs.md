# 合同领域知识与实现参考

本文件记录 `contract-toolkit` 的字段口径、抽取规则与实测教训 —— 写给要改规则或核对结果的人，不是用户文档。

版本：v1.0.1 · 最后更新 2026-10-08

---

## 1. 为什么合同比发票难一档

这不是感觉，是立项前实测出来的。同样跑三个「金额 + 甲乙方名称」的抽取任务，结果如下（脚本见开发期 `.workbuddy/tmp/contract_probe.py`）：

| 抽的东西 | 写法 A（规范条款式） | 写法 B（口语化正文） | 写法 C（表格版式） |
|---|---|---|---|
| 合同金额 | 抓到 `600000`，但**混入** `5` / `0.5` / `10`（「合同总价的 5%」把锚点带偏） | `88000` ✓，但混入 `20`（违约金比例） | **完全抽不到** |
| 甲乙方名称 | 4 个结果里 **3 个是垃圾**（「甲方支付预付款 30%」→ 把 `50`、`00`、`0%` 当名字） | 「甲方应于协议签署之日起**三日内**」→ 抽出「日内」 | 「广州鼎盛贸易有限公司」被**截成「公司」** |
| 全文金额候选 | 5 个，**无法自动判定哪个是总价** | 1 个 | **0 个**（`31,250.00` 后面没有「元」字，认不出是金额） |

**结论**：发票是半结构化数据（有固定字段名 + 结构化源），合同是**自由文本**。照抄 `invoice-toolkit` 的「锚点匹配直接定值」做法会翻车。

因此本技能的架构是：**先捞全部候选 → 打分消歧 → 低置信度显式上抛**，而不是直接定值。这个顺序是硬约束，不是可选的实现细节。

## 2. 合同台账字段口径（21 列）

「等级」列的含义：**确定** = 不依赖模糊判断，可直接用；**需核** = 有准确率上限，低于阈值进「待确认字段」。

| 列 | 来源与规则 | 等级 | 置信度基准 |
|---|---|---|---|
| 合同标识 | **源文件名**（去扩展名）。刻意不用合同编号 —— 大量存量合同没有编号 | 确定 | —— |
| 合同编号 | 锚点 `合同编号 / 协议编号 / 合同号 / 编号 / 文件编号` + 分隔符 | 需核 | 0.80 |
| 合同名称 | 标题行或文件名推断 | 需核 | 0.80 |
| 我方角色 | 需 `--our-name`；未提供则为空（不猜） | 需核 | 0.90（命中） |
| 对方名称 | 见 §4；未提供 `--our-name` 时取「先出现的角色」并在告警中说明 | 需核 | 0.92 / 0.72 / 0.55 |
| 统一社会信用代码 | 仅当合同里明写时（18 位大写字母数字） | 确定 | 0.90 |
| 合同金额 | 见 §3 | 需核 | 0.98（大小写一致）/ 0.92（仅大写）/ 0.85（仅数字） |
| 币种 | 人民币 / CNY / RMB / ¥ → `CNY`；无货币标记则不填 | 确定 | 0.80 |
| 税率 | 百分比，须落在 `VALID_RATES = (0, 1, 3, 5, 6, 9, 13)%` | 需核 | 0.90 |
| 签订/生效/到期日期 | 见 §5 | 需核 | 0.93（有锚点）/ 0.50（无锚点） |
| 合同期限(天) | **生效日期 → 到期日期**，自然日。只有终止日无起始日时不计算 | 确定 | —— |
| 付款方式 | 锚点 `付款方式 / 支付方式` 的原文片段 | 需核 | 0.70 |
| 质保金比例 | 锚点前置或后置双向匹配 | 需核 | 0.85 |
| 违约金比例 | 同上 | 需核 | 0.85 |
| 争议解决 | 锚点 `提交…仲裁委员会 / …人民法院` | 需核 | 0.75 |
| 源文件 | 完整路径 | 确定 | —— |
| 置信度 | 该行**关键字段**的整体置信度 | —— | —— |
| 待确认字段 | 逗号分隔的字段名清单（置信度 < 0.70 的） | —— | —— |
| 处理状态 | `正常` / `扫描件未提取` / `不支持格式` / `解析失败` / `无文本内容` | 确定 | —— |

### 为什么台账里会有「异常/未提取」的行

台账可以包含未提取成功的文件行（状态列标明）。这是**刻意**的：宁可多一行说明「这份没处理」，也不要让用户以为输入里本来就没有它。`--dry-run`、`处理 N 个文件：正常 X，异常/未提取 Y`、告警 sheet 三处口径必须一致。

**v1.0.1 修正**：`collect_files` 原先在目录模式下按 `SUPPORTED_EXT | LEGACY_DOC_EXT` 过滤，`.jpg` / `.xlsx` 之流在过滤阶段就被丢掉 —— 上面那句「宁可多一行」当时只对 `.doc` 成立。现改为**只排除隐藏文件与噪声目录**（`NOISE_DIRS` / `NOISE_FILES` / `is_noise()`），其余一律收进来并各占一行。三条口径由此恒等：

```
info 的「合计」 = parse 的「处理 N 个文件」 = 台账行数
```

该恒等由 `test_info_total_matches_parse_file_count` 钉住（同时断言 info 不再把 `.doc` 重复计入两个维度：`合计` 是总量，`需人工处理` 是它的子集）。

## 3. 金额抽取与消歧

### 3.1 什么才算「金额候选」

一个数字必须**带货币标记**才算候选。这是实测换来的：不带货币标记的裸数字会把「50 台」「30 个工作日」「5%」全卷进来。

货币标记包括：`人民币`、`元`、`万元`、`￥`、`¥`、`CNY`、`RMB`、大写金额（`陆拾万元整`）。

### 3.2 锚点分级（决定谁当选）

| 锚点类 | 例 | 处理 |
|---|---|---|
| **总价类** | 合同总价、总价款、合同总金额、合同价款、总额、总金额 | 加高分（最高权重） |
| 节点款 | 预付款、首期款、尾款、进度款、余款 | 明确降权，标注「属付款节点款，不是合同总价」 |
| 单价 | 单价、每台、每件、元/台 | 降权并标注「属单价」 |
| 税率/比例 | 税率、违约金、质保金、扣留 | 降权 |
| 无锚点 | 裸金额 | 基准分，通常不足以当选 |

打分结果**全部保留**在「抽取候选」sheet 的「候选得分」与「判定说明」列。实测样例 01 的得分：总价 `600000` 得 +12.00（采纳）、预付款 `180000` 得 +2.15、尾款 `420000` 得 +2.15、单价 `12000` 得 −1.22。

### 3.3 大小写交叉验证

同一**分句**内若同时出现中文大写金额与阿拉伯数字金额且数值一致，两者双向加分并升置信度到 0.98，判定说明追加「与同句大小写金额一致」；不一致则标注「同句存在不同金额，需人工确认」。

**分句边界是必须的**：早期版本以「位置 ±60 字符」为窗口，导致被采纳的 `600000` 因隔壁条款的 `180000` 被误标「同句存在不同金额」。

## 4. 当事人名称抽取

三层约束叠加，少一层就会出垃圾结果：

1. **组织名后缀必须命中词表**（`ORG_SUFFIX`，47 个）：
   `有限责任公司 / 股份有限公司 / 有限公司 / 集团有限公司 / 集团公司 / 合伙企业 / 有限合伙 / 普通合伙 / 个人独资企业 / 公司 / 集团 / 企业 / 工厂 / 厂 / 商店 / 商行 / 店 / 事务所 / 研究院 / 设计院 / 研究所 / 科学院 / 大学 / 学院 / 学校 / 中学 / 小学 / 幼儿园 / 医院 / 卫生院 / 诊所 / 疾病预防控制中心 / 银行 / 支行 / 分行 / 信用社 / 农村商业银行 / 中心 / 合作社 / 协会 / 工会 / 委员会 / 工作室 / 管理处 / 律师事务所 / 会计师事务所 / 税务师事务所`
2. **角色词必须与名称在同一行内**（`ROLE_WORDS`，31 个）：
   `甲方 / 乙方 / 丙方 / 丁方 / 需方 / 供方 / 买方 / 卖方 / 购方 / 销方 / 委托方 / 受托方 / 委托单位 / 受托单位 / 发包方 / 承包方 / 发包人 / 承包人 / 出租方 / 承租方 / 出借方 / 借款方 / 采购方 / 供应商 / 采购人 / 中标人 / 招标人 / 用人方 / 受聘方 / 出让方 / 受让方`
3. **优先取紧邻分隔符**（`：`、空白）的那个，且角色词按长度倒序匹配（「采购方」优先于「方」）

置信度分档：

| 命中情况 | 置信度 |
|---|---|
| 角色词 + 分隔符 + 组织名后缀 | 0.92 |
| 组织名后缀 + **同行**角色词 | 0.72 |
| 只有组织名后缀（同行无角色词） | 0.55 |

### 实测过的两类错

- **跨行关联**（已修）：「采购方」被错配给下一行的乙方公司名；「甲方」被配给「提交北京仲裁委员会」。修法是角色词限定在同一行内。
- **机构名不是当事人**（未修，属边界）：「XX仲裁委员会」「XX中心」也以词表后缀结尾，会被当成当事人候选，置信度 0.55 —— 低于 0.70 阈值，会进「待确认字段」，属于「报出来让人判断」而非「猜错」。

## 5. 日期抽取与归类

### 5.1 锚点表（`DATE_ANCHORS`）

| 字段 | 锚点 |
|---|---|
| 签订日期 | 签订日期 / 签署日期 / 订立日期 / 签约日期 / 签订时间 / 签署时间 / 签订于 / 签署于 / 订立于 / 签订 / 签署 / 签约 |
| 生效日期 | 生效日期 / 生效日 / 生效时间 / 开始日期 / 起始日期 / 起始日 |
| 到期日期 | 有效期限至 / 有效期至 / 终止日期 / 到期日期 / 到期日 / 届满日 / 截止日期 / 届满 / 有效期限 / 服务期限至 |

### 5.2 后置锚点优先（合同特有）

合同里日期常写在锚点**前面**：「本合同自 2026-10-01 起生效」「自 2026-10-01 起至 2027-09-30 止」。所以必须先看日期**之后**的文字（`_post_anchor`），再看**之前**的（`_pre_anchor`）。

后置规则表（按顺序匹配）：

| 后缀形态 | 归类 |
|---|---|
| `起…至` / `起…到` | 生效日期（区间起点） |
| `起（之日/之日起）（正式/即/自动/均/同时/双方）生效` | 生效日期 |
| `起算` / `起计算` | 生效日期 |
| `自/从 X 起` + 句读或后续 | 生效日期（**必须由「自/从」门控**，否则会误伤「交货期 30 日起算」这类期限窗口） |
| `至/到 YYYY` | 生效日期（「自…至…」区间起点） |
| `（之日/当日/即日）生效/执行/适用` | 生效日期 |
| `签订/签署/订立/签约` | 签订日期 |
| `止/届满/终止/截止/到期` | 到期日期 |

### 5.3 三个必须守住的细节

1. **`DATE_RE` 末尾不能用 `\s*日?`** —— `\s` 会吃掉换行，导致日期的「后缀窗口」越到下一行：「生效日期：2026-10-01\n到期日期：2027-09-30」里第一个日期被下一行的标签抢走。必须写成 `[ \t]*日?`。
2. **前置锚点只在同一行内查找** —— 否则上一行残留的「签订日期」会抢走本行的日期。
3. **同句兼报** —— 「（X）起生效」这类写法里 X 既是签订日也是生效日，主报**生效日期**、同时以 0.70 置信度兼报签订日期。两列都不落空，但不会顶掉文档里真正写着「签订日期：」的那处。

### 5.4 五种写法回归（23 条对抗性用例，见测试分节 7）

已覆盖：「签订日期：X」「自 X 起生效」「自 X 起正式生效」「自 X 至 Y 止」「自双方签署之日（X）起生效」「于 X 起 90 日内」「有效期 X 年，自 Y 起算」「交货期 30 日」（**不得**被判成生效日期）。

## 6. 付款节点

### 6.1 节点锚点

`预付款 / 首付款 / 首期款 / 预收 / 尾款 / 余款 / 进度款 / 第一期 / 第二期 / 第三期 / 分期 / 定金` → 类型 `支付节点`
`质保金 / 保证金 / 押金` → 类型 `扣留项`

### 6.2 两个关键约束

1. **窗口必须落在同一分句内**。原文「余款于项目验收通过后十日内付清。服务期限……任何一方违约支付 20% 违约金」—— 早期版本以「锚点后 90 字符」为窗口，把后一条款的 20% 当成了余款的付款比例，导致「比例合计 60%」。现用 `_clause_bounds` 收窗。
2. **扣留项不计入「比例合计 = 100%」**。质保金是从尾款中扣留的，不是独立支付节点。计入会导致「比例合计 105%」误报。

### 6.3 约定时点

`\d{1,3} 个工作日/日/天` → 「N 个工作日内」/「N 日内」；`\d{1,3} 个月/年` → 「N 个月内」/「N 年内」。

### 6.4 金额语义

「固定金额」表述里的「定金」「订金」与付款节点锚点冲突，曾导致误命中。加词边界约束。

## 7. 体检规则口径

| 规则 | 级别 | 判据 | 分母 |
|---|---|---|---|
| 节点合计 | 高 | 付款节点金额合计 = 合同金额（`--tolerance`，默认 0.01） | 有合同金额且有节点金额的行 |
| 比例合计 | 中 | 付款节点比例合计 = 100%（**扣留项不计入**） | 有比例数据的行 |
| 日期逻辑 | 高 | 签订 ≤ 生效 ≤ 到期 | 相关日期都齐全的行 |
| 金额为正 | 高 | 合同金额 > 0 | 有金额的行 |
| 大写一致 | 高 | 中文大写金额 = 台账采纳金额 | 同时有大写候选项与采纳值的行 |
| 税率区间 | 低 | 税率 ∈ `VALID_RATES` | 有税率的行 |
| 关键字段 | 高 | 对方名称与合同金额非空 | 全部行 |
| 到期状态 | 中 | 到期日期是否已过 | 有到期日期的行 |

### 「校验行数」为什么小于总行数

分母是**有数据可校验的行数** —— 缺数据的行既不冒充通过，也不算不通过，而是由「关键字段」规则统一抓出。汇总表**没有**单独的「不适用」列，别把「校验行数 < 总行数」误读成漏检。

## 8. 置信度与「待确认字段」

- 阈值 **0.70**（v1.0.2 起可用 `--conf-threshold` 调，取值 `(0, 1]`）：低于此值的字段名进入「待确认字段」列（逗号分隔）
- 阈值同时用于：xlsx 的问题行条件着色、HTML 报告的同行标底色、`--probe` 的 `!!` 标记、以及 `parse` 结尾的提醒文案。**四处加上 `ContractRecord.pending` 共五个落点，统一读模块级 `CONF_THRESHOLD`**，由 `main()` 一处校验写入 —— v1.0.1 时它是硬编码在这五个地方的，一致性只能靠人记住（典型的「改一处漏四处」结构）
- **不设「整体自动可信」的开关** —— 低置信度一律显式列出，不用「置信度高的自动采纳、低的才提示」这类隐式策略
- 阈值不是越高越好：调得过高，整列都是「待确认」而失去信号；调得过低，真正的低质量抽取就混过去了。按批次的合同质量定，先跑默认值看「待确认字段」列的分布再决定

## 9. 测试样本构造指南

`examples/make_samples.py` 现场生成四份，覆盖四种典型形态与边界（全部纯文本，可直接被 `parse` 处理）：

| 样例 | 形态 | 刻意覆盖的边界 | 实测预期 |
|---|---|---|---|
| 01 | 规范条款式 | 当事人、编号、金额、日期、付款节点齐全；含「合同总价的 5%」诱饵与单价 | 金额 600000（0.98）、三日期齐、期限 364 天、违约金 0.50% |
| 02 | 口语化正文式 | 委托方是个人（无组织名后缀）；只有「总额 + 比例」，无条款标题 | 只写首期款 40% → 比例合计**应当**报不通过 |
| 03 | 表格版式 | 金额数字后无「元」字，只能靠大写兜底 | 金额 31250（0.92）；编号、生效/到期日期**抽不到** |
| 04 | 框架协议 | 金额与期限都未约定 | 金额空、置信度 0 → **正确行为**，不是抽取失败 |

**判断「不通过是不是缺陷」的方法**：先看该样例是否**刻意**如此。02 与 04 报的 2 处问题都是设计意图，`check` 报出来正是它的职责。

### 断言方向

- 中文大写金额解析：含零 / 含万-亿分级 / 含角分 / 连续零 / 缺「整」/ 错别字
- 金额消歧：**「合同总价的 5%」不得当选**；单价与节点款不得当选；大小写一致时置信度升到 0.98
- 当事人：跨行角色词**不得**关联；「甲方支付预付款 30%」不得抽出垃圾名；机构名候选置信度 < 0.70
- 日期：23 条对抗性用例逐条断言期望字段；含一条元测试「正则不吞换行」
- 付款节点：跨句比例不得混入；扣留项不计入 100%
- 未处理文件：目录模式 `.doc` 必须计入「异常/未提取」

## 10. 实测教训（只有跑起来才会暴露）

1. **修完一个缺陷会引入新回归**。「生效日期」修好后，`DATE_RE` 吞换行导致「生效日期/到期日期」相邻标签串位 —— 表面看是修好了三个用例，实际破坏了另一类。所以修完必须跑**同类对抗性用例全集**，不能只跑刚失败的三个。
2. **「修掉三个案例」≠「逻辑正确」**。三类写法修完后补了 23 条对抗性用例，又挖出一个同类缺口（「自 X 起 90 日」的起点不归类）。
3. **放宽规则要考虑误伤**。为支持「自 X 起…」而放宽「起」，会误判「交货期 30 日起算」—— 加「自/从」门控才安全。
4. **同一份文件被并行写坏过**（开发期工具问题）：两个写操作同时指向同一个 `.py`，内容交错损坏。批量生成脚本时要串行。
5. **`write-only` 模式不能混用 `WriteOnlyCell` 与普通值**，lxml 序列化器会错乱。
6. **空值写空字符串会让整列 dtype 变 `object`**（pandas 读回后无法求和），必须写真空单元格。
7. **退出码要用重定向或 `PIPESTATUS` 取**，管道会吞掉前一个命令的退出码。
8. **`pytest --basetemp` 只建父目录**：预建叶子目录会逼 pytest 去删它 → 撞沙箱删除拦截 → 大批用例 `ERROR at setup`（看起来像大面积回归，实际是环境问题）。且路径不要含 `tmp` 字样。
9. **文档里引用的子命令要真去敲一遍**：`SKILL.md` 曾写着用 `reconcile-toolkit link` 做付款核销，而该技能的子命令是 `rule` / `recon` / `summary` / `info` / `check` —— **根本没有 `link`**。跨技能引用是 `check_examples` 的盲区（它只校验本技能的脚本），只能靠人敲。补核销示例时顺手跑了一遍才发现。
10. **help 文字与实际行为不一致，比没有 help 更糟**：`--recursive` 的 help 写着「默认开启」，实现却是 `store_false` 配 `recursive=not args.no_recursive` —— 实际默认**不**递归。没有 help 时用户会去试；help 写反了用户就信了，而后果是子目录里的合同被静默漏收。
11. **新增「读环境变量 / 读配置文件」能力时，必须同步隔离测试环境**：v1.0.2 加了 `CONTRACT_OUR_NAME` 与 `.contract-toolkit.yaml` 之后，本机一旦配过，所有 parse 用例的甲乙方判定都会跟着变 —— 测试只是碰巧在本机通过。现已加 `autouse` fixture 挡掉环境变量、配置文件与模块级阈值。
12. **键选错时工具不会报错，只会安静地说「全都不匹配」**：拿台账的「合同标识」（文件名）去对流水里的「合同编号」，实测得到 0 个匹配。凡演示跨表对账的文档都要写明这条，否则用户只会怀疑自己的数据有问题。
13. **告警的判据要留反向用例**：表格版式提示的条件是「关键字段真的缺了」+「文本确实带表格特征」，第二个条件是防止每份不写金额的框架协议都背一条噪声告警。**告警一旦开始误报，用户就不再逐条看，等于没有告警** —— 所以测试里既要有正例，也要有「普通条款式合同一条表格告警都不该有」的反向断言。
