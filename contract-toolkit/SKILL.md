# 合同要素台账技能

## 目的

把**已经签完、散在各人电脑里**的存量合同，一次变成可筛选、可核对、可提醒的结构化台账。

要解决的不是「怎么签合同」（那是电子签平台的事），而是「手里这堆 PDF 到底约定了什么、什么时候到期、付款节点对不对得上」。合同签完就归档、要找的时候翻不出来、到期了没人知道 —— 这些是台账能解决的。

与 `invoice-toolkit` 的分工：发票是半结构化数据（有固定的字段名和结构化源），合同是**自由文本**，所以本技能的定位与实现都是「先把候选全捞出来、再消歧、低置信度显式上抛」，而不是假装能 100% 自动抽准。

## 实现状态（v1.0.2）

已实现 5 个子命令，全部为确定性规则，无模型调用、无联网：

| 子命令 | 作用 | 输出 |
|---|---|---|
| `info` | 依赖自检 + 目录摸底（含扫描件识别） | 终端 |
| `parse` | 抽取要素并生成台账 | 4 sheet xlsx / csv / html |
| `check` | 台账体检（8 条确定性规则） | 体检汇总 + 问题明细 |
| `expire` | 到期清单（按期分档） | 到期清单 |
| `compare` | 跨合同汇总与要素一致性比对 | 分组汇总 + 要素分布 |

单测 167 全绿。抽取逻辑全部按实测缺陷反向加固（见 `references/specs.md`）。

v1.0.2 补齐的是「用起来顺不顺手」这一类，不是新抽取能力：

- **置信度阈值可调** —— `--conf-threshold`（默认 0.70）。不同批次的合同质量差很多，
  写得很规范的批次可以调高，逼你多看几眼待确认字段；写得散的批次可以调低，免得
  整列都是「待确认」而失去信号
- **目录递归默认开启** —— 合同按年份、按对手方分目录存放是常态。旧版要显式加
  `--recursive` 才收子目录，而 help 文字写的是「默认开启」，**按 help 理解就等于
  子目录里的合同被静默漏掉**。现在默认递归，用 `--no-recursive` 只处理当前层
- **我方名称可配一次** —— `--our-name` 之外，支持环境变量 `CONTRACT_OUR_NAME`
  与 `.contract-toolkit.yaml`，省掉每批手敲；命中的默认值会**显式打印来源**
- **表格版式定向提示** —— 金额/日期抽不到、且文本确实带表格特征时，告警里直接
  告诉你去用 `pdf-toolkit tables`
- **HTML 报告** —— 输出路径写 `.html` 即得单文件自包含报告，给不装 Excel 的人看

## 适用场景

- 行政/法务/采购手里积累了一批合同 PDF，要做一份总台账
- 想知道**哪些合同快到期了**，或已经到期却没人管
- 核查某份合同里写的付款节点比例、金额加起来对不对
- 同一批合同要检查「同一个对手方签的合同，违约金比例是不是各写各的」
- 归档前做一次体检：金额、日期、编号有没有缺漏或明显矛盾

## 能力边界（务必先读）

### 第一层 · 确定性可做，结果可直接使用

这些不依赖模型、不存在准确率问题：

- **中文大写金额解析** —— 「陆拾万元整」「壹拾万零伍佰元零叁角」等写法，含零、含万/亿分级、含角分、连续零、缺「整」字、常见错别字
- **阿拉伯金额归一** —— 千分位、全角、货币符号、前后缀
- **台账体检的 8 条规则** —— 付款节点金额合计 vs 合同金额、比例合计、日期逻辑链（签订 ≤ 生效 ≤ 到期）、金额为正、大写与数字一致、税率区间、关键字段完整性、到期状态
- **到期日计算与分档** —— 合同期限（天）、已到期 / 即将到期 / 正常（未到期）
- **要素一致性比对** —— 同一分组内某要素存在多个取值时报出来

### 第二层 · 需人工确认，只报结果不下结论

这些**有客观准确率上限**，因为合同是自由文本。本技能的做法是：给出取值 + 置信度 + 原文片段，并保留全部落选候选。

| 要素 | 实际表现（实测） |
|---|---|
| **当事人名称** | 规范写法（「甲方（采购方）：北京星辰科技有限公司」）准确；但无角色词时会混入噪声（实测出现过「提交北京仲裁委员会」被当成组织名，置信度 0.55）。**没有角色词或名称不像组织名的，必须人工核** |
| **合同金额（总价）** | 有总价类锚点（「合同总价」「总价款」「合同总金额」）时可靠；但同一份合同里会同时出现单价、税率、节点款、违约金比例，靠锚点打分区分。**实测「合同总价的 5%」这类表述会把比例带进候选**，虽已按锚点降权，仍需看「抽取候选」sheet |
| **签订/生效/到期日期** | 有明确标签（「签订日期：」）或结构（「自 X 起生效」「自 X 至 Y」）时可靠；**表格版式里若无标签则抽不到** |
| **付款节点** | 规范写法（「支付预付款 30%」）可靠；口语化表述（「先付三成」）抽不到 |
| **质保金/违约金比例** | 锚点前置或后置都能命中（已支持双向），但同一句里多个百分比时可能取错 |

**判断方法**：`parse --probe` 会逐字段打印取值与置信度，先对 1–2 份跑一遍再批量处理。

### 第三层 · 不做（能力边界与合规红线）

1. **不做条款风险审查。** 判断「这条对我方是否不利」需要立场和法律判断，不是事实抽取。混在一起会让技能定位模糊（台账只要事实），而且这块已有专业产品在做。
2. **不做合同效力与续签判断。** 出具这类意见有法律责任。本技能只报「到期日期是 X」，不报「这份合同应该续签」。
3. **不内置 OCR。** 扫描件请先用 `pdf-toolkit` 的 `text --ocr` 转文本。理由见下。
4. **不生成或修改任何合同文本。** 台账是只读派生，不反向写回合同。
5. **不联网。** 合同是敏感商业数据，本技能全程本地运行。

### 关于「为什么不做 OCR」

`pdf-toolkit` 已经有 `text --ocr`（只对字符数低于阈值的页面识别，且 `ocr_status()` 会自检、缺依赖时明确报错而不静默失败），所以**扫描件是可处理的**，两步走：

1. **把纸变成字** —— 用 `pdf-toolkit` 技能的 `text` 子命令，输入扫描件 PDF、输出 txt 并开启 OCR。该技能不在本包内，需另行安装（同作者的技能，`--ocr` 依赖系统层的 tesseract + chi_sim）：
   `text <扫描合同.pdf> <扫描合同.txt> --ocr`
2. **把字变成台账** —— 用本技能处理转出来的文本：

```bash
python scripts/contract_toolkit.py parse 扫描合同.txt 台账.xlsx
```

不在本技能内置 OCR 的理由有三条：① 会让「零重型依赖」的口碑破功（tesseract 需系统层安装）；② OCR 的准确率无法承诺，而本技能的置信度体系是要能兑现的；③ 职责分离 —— pdf-toolkit 负责「把纸变成字」，本技能负责「把字变成台账」，各自的能力边界都更清楚。

`info --probe-text` 会**主动识别无文本层的 PDF** 并单独列出来，不会让你在 parse 之后才发现少了几份。

### 关于「当事人名称准确率」

这是本技能最弱的一环，必须写清楚：合同里甲方乙方常写成「甲方」「乙方」后用括号、换行、空格各种排布，还有「需方/供方/委托方/受托方/出租方/承租方」等十余种角色词。纯正则匹配会出两类错：

- **漏** —— 名称与该角色词的相对位置不在预期的窗口内
- **错** —— 窗口内有多个组织名，或把「XX仲裁委员会」这类机构当成当事人（它们也以「委员会」「中心」等后缀结尾）

实现的应对：角色词必须与名称**在同一行内**（跨行关联会错得很离谱，实测过），并优先取紧邻分隔符（`：`、空白）的那个；组织名必须命中后缀词表（公司/企业/厂/中心/事务所/合伙企业/个体工商户…）。即便如此，**甲方乙方角色依赖 `--our-name` 才能准确区分**：不给我方全称时，只能按「先出现的角色」猜，并会在告警里明说这一点。

**强烈建议**：处理批量合同时始终带 `--our-name "我方公司全称"`。这一条能把「我方角色 / 对方名称」两列从「猜」变成「定」。

不想每批都手敲，可以配一次，按下面的优先级取（**命令行 > 环境变量 > 配置文件**）：

```bash
export CONTRACT_OUR_NAME="北京星辰科技有限公司"          # 环境变量
```

或在合同目录（或其上级目录、当前目录、用户主目录）放一个 `.contract-toolkit.yaml`：

```yaml
# 我方主体，用于区分甲乙方
our_name: 北京星辰科技有限公司
```

配置文件刻意**不引 PyYAML**（本技能的卖点之一是零重型依赖），只认 `键: 值` 这种单层写法，`#` 起注释；内容以 `{` 开头时按 JSON 读。
命中默认值时会打印来源，例如 `我方名称：北京星辰科技有限公司（取自环境变量 CONTRACT_OUR_NAME；用 --our-name 可覆盖）` —— **静默套用配置比不套用更危险**，你会以为台账里的甲乙方是自己当场指定的。

## 输入格式与确定性排序

| 格式 | 支持情况 | 依赖 |
|---|---|---|
| `.txt` / `.md` | 完整支持 | 无（自动尝试 utf-8-sig / utf-8 / gb18030 / gbk / big5） |
| `.docx` | 完整支持（正文段落 + 表格文本） | `python-docx`（可选） |
| `.pdf` | 支持**有文本层**的 PDF | `pypdf`（可选） |
| `.pdf`（扫描件） | **不处理**，在 `info --probe-text` 与 `parse` 中明确标出 | 需先用 pdf-toolkit 转文本 |
| `.doc` | **不处理**，明确报错并给出转换方法 | 需另存为 `.docx` 或带文本层的 PDF |
| 其它扩展名 | **不处理**，逐个列出原因 | —— |

**重要（v1.0.1 修正）**：目录模式下**不做扩展名过滤** —— 只要不是隐藏文件或噪声目录（`.git` / `node_modules` / `__pycache__` / `~$` 临时文件 / `Thumbs.db`），一律收进来并以「异常/未提取」计入台账，**不会静默跳过**。目录里混着 `附件清单.xlsx`、`照片.jpg` 这类文件时，`info` 会逐个列出并说明原因，`parse` 会给它们各写一行台账（状态为 `不支持格式`），保证「输入里有什么」和「台账里有几行」对得上。

> v1.0.0 只对旧版 `.doc` 做了这件事，其它扩展名在过滤阶段仍被丢掉 —— 于是上面这段承诺**在 v1.0.0 里是没兑现的**：实测一个 5 文件目录只产出 3 行台账，`照片.jpg` 与 `附件清单.xlsx` 无声消失。同一类缺陷只修了一半。v1.0.1 起改为统一口径，并有单元测试钉住（`test_collect_files_collects_all_non_noise_files` / `test_info_total_matches_parse_file_count`）。

**为什么可以放心不做扩展名过滤**：噪声目录与隐藏文件被排除，所以把一个含 `node_modules` 的目录误指进来，也不会产出几千行台账。真要处理单个不常见扩展名的文件，直接把它当参数传进来即可（单文件模式不做任何过滤）。

排序：目录内按「父目录名 → 文件名」的字典序处理（小写归一），同一目录多次运行顺序一致。

**子目录默认一并处理**（v1.0.2 起）。合同按年份、按对手方分目录存放是常态，旧版要显式加 `--recursive` 才收子目录，而 help 文字写的是「默认开启」—— 按 help 理解不传参，子目录里的合同就此消失且没有任何提示，属于典型的静默漏收。现在默认递归，要只处理当前层用 `--no-recursive`。`info` 会在摸底结果里直接写明本次的处理范围。

## 环境准备

```bash
# 必需
python -m pip install "pandas>=2.0" "openpyxl>=3.1"

# 按需（不装不影响核心功能，用到时会明确报错）
python -m pip install "pypdf>=5.0"          # 读 PDF
python -m pip install "python-docx>=1.1"    # 读 .docx

# 自检（会告诉你缺什么、装什么）
python scripts/contract_toolkit.py info
```

要求 Python ≥ 3.10。**不引入** PyMuPDF（AGPL）、easyofd、pytesseract、paddleocr、ollama。

## 使用流程

### 第一步：自检与摸底（info）

```bash
python scripts/contract_toolkit.py info ./合同
```

实际输出（样例目录，四份纯文本合同）：

```
contract-toolkit v1.0.1
==============================================================
依赖自检：
  [OK  ] pandas    
  [OK  ] openpyxl  
  [OK  ] pypdf     
  [OK  ] docx      
  说明：pypdf 缺失则无法读 PDF；python-docx 缺失则无法读 .docx。
  本技能不做 OCR，扫描件请先用 pdf-toolkit 的 text --ocr 转文本。

目录摸底：D:\...\samples
  txt               4 个
  -------------- ----
  合计                4 个

  提示：加 --probe-text 可实际读一遍文件，统计文本层覆盖率与扫描件占比。
```

**「合计」= 目录内实际文件数**（已排除隐藏文件与 `.git` / `node_modules` / `__pycache__` 这类噪声目录），并且它与 `parse` 的「处理 N 个文件」、台账行数**三者恒等** —— 这是刻意设计，见下。

**处理真实合同前先跑 `--probe-text`** —— 它会实际读一遍，把无文本层的 PDF 单列出来。混着不可处理文件的目录会是这样：

```
目录摸底：D:\...\edge
  doc(旧版)           1 个
  txt               1 个
  其它格式              2 个
  md                1 个
  -------------- ----
  合计                5 个（1 个旧版 .doc 需先转换、2 个格式不支持，不会参与抽取）

  需人工处理 3 个（这些文件仍会进台账，状态列为「不支持格式」）：
      · 旧版合同.doc —— 旧版 .doc 格式，需另存为 .docx 或带文本层的 PDF 后再处理
      · 照片.jpg —— 不支持的扩展名 .jpg
      · 附件清单.xlsx —— 不支持的扩展名 .xlsx
```

## 输出说明

`parse` 写出 4 个 sheet，三种输出格式按接收方选：

- **`.xlsx`**（推荐）—— 多 sheet 一个文件，表头配色、冻结首行、条件着色
- **`.csv` / `.tsv`** —— 退化为同名多文件（如 `台账__合同台账.csv`），命令会逐个打印真实路径
- **`.html`** —— 单文件自包含报告，内联 CSS、零外部资源，双击用浏览器打开即可

csv 给要接着做数据处理的人，html 给**只想知道结论、没装 Excel/WPS** 的人。

**① 合同台账**（21 列，一份文件一行）

| 列 | 说明 |
|---|---|
| 合同标识 | 源文件名（去扩展名），台账与付款节点表的关联键 |
| 合同编号 | 从「合同编号/协议编号/合同号」等锚点抽取；很多存量合同没有 |
| 合同名称 | 从标题或文件名推断 |
| 我方角色 / 对方名称 | 需 `--our-name` 才能准确区分；未提供时按先出现的角色猜并在告警中说明 |
| 统一社会信用代码 | 仅当合同里明写时才有 |
| 合同金额 / 币种 | 总价类锚点 + 大小写交叉验证后的取值 |
| 税率 | 百分数 |
| 签订日期 / 生效日期 / 到期日期 | ISO 格式（YYYY-MM-DD） |
| 合同期限(天) | 生效 → 到期，按自然日计算 |
| 付款方式 | 命中「付款方式/支付方式」锚点的原文片段 |
| 质保金比例 / 违约金比例 | 百分数 |
| 争议解决 | 仲裁机构或法院表述 |
| 源文件 | 完整路径 |
| **置信度** | 该行关键字段的整体置信度（低于阈值即进「待确认字段」，阈值由 `--conf-threshold` 控制，默认 0.70） |
| **待确认字段** | 逗号分隔的字段清单，直接告诉你该核哪几个 |
| **处理状态** | `正常` / `扫描件未提取` / `不支持格式` / `解析失败` / `无文本内容`（五类，与代码一致；任何非「正常」的行都会在「解析告警」sheet 里给出原因） |

**② 付款节点**（9 列）：合同标识 / 节点序号 / 节点名称 / **节点类型** / 比例(%) / 金额 / 约定时点 / 置信度 / 原文片段

`节点类型` 分两类：`支付节点`（预付款、尾款、进度款…）与 `扣留项`（质保金、保证金、押金）。**`扣留项` 不参与「比例合计 = 100%」的计算** —— 质保金是从尾款里扣留的，不是独立的支付节点，计入会导致「比例合计 105%」这类误报。金额列是**数值类型**，可直接在 Excel 里求和。

**③ 抽取候选**（9 列）：合同标识 / 字段 / 是否采纳 / 候选值 / 命中锚点 / 候选得分 / 置信度 / 判定说明 / 原文片段

**这是本技能最重要的一个 sheet** —— 全部落选候选都在这里，每一条都能追溯到原文片段和打分理由。抽错了可以直接看到「为什么选了 A 没选 B」。

**④ 解析告警**（4 列）：合同标识 / 源文件 / 状态 / 告警内容

样式与 `invoice-toolkit` 一致：表头绿底（`1FA055`）白字、首行冻结、列宽按内容自适并上限 42 字符、低置信度与高危问题行条件着色。

`check` 输出 2 个 sheet（体检汇总 / 问题明细），`expire` 与 `compare` 各 1–2 个，均已在上面各步说明。

### HTML 报告

输出路径写 `.html` 就得到一份单文件自包含报告，`parse` / `check` / `expire` / `compare` 都支持：

```bash
python scripts/contract_toolkit.py check ./合同台账.xlsx ./合同体检.html --as-of 2026-10-08
```

它把所有 sheet 平铺成一页（每个 sheet 一个区块），表头绿底与 xlsx 保持一致，低置信度与异常行同样标底色。两点刻意的设计：

- **零外部资源** —— 不引 CDN、不引字体，断网也能看，整份报告就是一个文件，可以直接发给别人
- **超长表只预览前 300 行并注明** —— 几百份合同的台账若全量内联，单文件会膨胀到几十 MB，浏览器打开就卡；完整数据本来就在同名的 xlsx / csv 里

### 置信度阈值怎么调

`--conf-threshold`（默认 `0.70`，取值 `(0, 1]`）决定哪些字段进「待确认字段」列、哪些行标底色：

```bash
# 这批合同写得很规范，提高门槛，逼自己多看几眼
python scripts/contract_toolkit.py parse ./合同 ./台账.xlsx --conf-threshold 0.85

# 这批写得很散，降低门槛，免得整列全是「待确认」而失去信号
python scripts/contract_toolkit.py parse ./合同 ./台账.xlsx --conf-threshold 0.55
```

**怎么选**：先按默认跑一遍，看「待确认字段」列的分布。如果一列里全是「对方名称、合同金额」（每行都有），说明阈值对你的批次偏高，该降；如果几乎全空、你却知道这批合同写得很随意，说明偏低了，该升。`check` 也接受这个参数，用来控制报告里标底色的行。

## 关键约定

- **不做模糊匹配。** 与 `reconcile-toolkit` 同一条红线：猜错键比多报差异严重得多。当事人名称只做词表+角色+区域约束的确定性匹配，不做相似度。
- **空值不参与任何计算。** 金额缺失就不进「节点合计」的分母（也就不会拿 0 去比）；日期缺失就不进日期逻辑链。
- **金额比对容差默认 0.01**，可用 `--tolerance` 调整，避免浮点噪声被报成差异。
- **金额与日期在 xlsx 里是数值/日期类型**，不是字符串 —— 可直接求和、可直接排序。
- **台账包含未提取成功的文件行**（状态列标明）。这是刻意的：宁可多一行说明「这份没处理」，也不要让你以为输入里本来就没有它。**v1.0.1 起这条对所有格式成立**（此前只对旧版 `.doc` 成立，`.jpg` / `.xlsx` 仍被静默丢弃）。由此 `info` 的「合计」、`parse` 的「处理 N 个文件」、台账行数三者恒等。
- **「合同标识」用文件名而不是合同编号** —— 很多存量合同根本没有编号，用编号会让去重和关联失效。
- **一份合同对应多个文件**（正文 + 附件 + 补充协议）时，当前版本会各自产出一行，不会自动合并。**这是已知的局限**：合同缺少天然唯一标识，合并只能靠「对方名称 + 金额 + 签订日期」这类弱键，宁可先不合并，也不要猜错。

## 权限与安全

- **纯本地**：不联网、不上传、不调用任何外部接口
- **只读**：只读取你指定的合同文件，不修改、不移动、不删除任何源文件
- **写出位置**：只写你指定的输出路径（以及 csv 模式下的同名多文件）
- **数据等级**：合同含商业条款与金额，按 L3 敏感数据对待；不写入临时目录、不在日志中留存全文
- **不生成合同文本**：台账是只读派生，不会反向写回
- **无 OCR、无模型**：不引入任何需要上传文件的能力

## 与配套技能的关系

本技能补齐了「票 - 账 - 钱」闭环里缺的第三块：

| 技能 | 管什么 | 与本技能的关系 |
|---|---|---|
| `pdf-toolkit` | 把 PDF 变成文本/表格/图片 | **上游**：扫描件先用它的 `text --ocr` 转文本 |
| `excel-toolkit` | 表格清洗、转换、透视 | **上游/下游**：台账可交给它做进一步清洗或透视 |
| `invoice-toolkit` | 增值税发票台账与勾稽 | **平行**：发票记「花了多少、能抵多少税」 |
| **`contract-toolkit`** | 合同要素与付款节点 | **本技能**：合同记「约定了什么、什么时候付、什么时候到期」 |
| `reconcile-toolkit` | 两表对账与单表体检 | **下游**：用它的 `recon` 子命令做付款核销（见下） |
| `skill-preflight-check` | 上架前体检流程 | 本技能自身的发布流程 |

### 付款核销怎么跑（可照抄）

本技能只负责产出数据，**核销判定交给 `reconcile-toolkit`**。示例流水可以用
`examples/make_payment_samples.py` 现场造一份（默认写到 `examples/samples/`）：

```bash
python examples/make_payment_samples.py ./samples/示例银行流水.csv
```

再把它和台账的「合同台账」sheet 对起来。键用 **合同编号**，金额按同键汇总
（`--aggregate` 就是为「一份合同对多笔流水」这种核销场景准备的）：

```bash
python <reconcile-toolkit 目录>/scripts/reconcile_toolkit.py recon \
    合同台账.xlsx "示例银行流水.csv" 核销结果.xlsx \
    --left-sheet 合同台账 --on 合同编号 \
    --left-amount 合同金额 --right-amount 金额 \
    --aggregate --tolerance 0.01
```

实测输出（四份样例合同 + 四笔流水）：

```
============================================================
 差异类型  记录数    占比
   匹配    0  0.0%
 金额不符    1 20.0%
 仅右表有    1 20.0%
左表键缺失    3 60.0%
============================================================
匹配 0 / 共 5 个键  (0.0%)
金额差异合计(绝对值): 20,000.0
```

**三类结果都要会读**：

- **金额不符 1** —— `XC-2026-1001` 实付合计 580,000，合同金额 600,000，差 20,000。这就是「该付的没付够」
- **仅右表有 1** —— 流水里的 `HT-2026-0007` 在台账中找不到对应合同（该合同本身没写编号）
- **左表键缺失 3** —— 三份合同没有编号，编号列为空。**空键不参与配对**，所以被单独归类而不是拉去随便配一个：猜错键比多报几行严重得多

**为什么不拿「合同标识」当键**：台账的「合同标识」是文件名（存量合同常常
没有编号，拿编号当主键会让去重与关联失效），而流水里写的是合同编号，两者字面上
对不上 —— 实测用「合同标识」做键会得到 **0 个匹配**。这个坑值得记住：
键选错了，工具不会报错，只会安静地告诉你「全都不匹配」。

付款节点级的核销（预付款、尾款各自对应哪几笔）需要节点级的唯一键。建议先把
台账的「付款节点」sheet 导出，按「合同标识 + 节点名称」拼一列键再对 ——
本技能不替你拼这列，因为**拼错键的代价比不拼大**。

三条可做的勾稽：

1. **合同付款节点 vs 银行流水** —— 该付的付了没（上面的实操）
2. **合同金额 vs 发票台账合计** —— 该开票的开够没（`invoice-toolkit` 出台账，同样用 `recon --aggregate`）
3. **合同到期日 vs 当前日期** —— 该续的续了没（`expire` 已直接给出）

## 进阶问题排查

| 现象 | 原因与处理 |
|---|---|
| 对方名称抽成了「XX仲裁委员会」 | 机构名也以「委员会/中心」结尾。看置信度（这类通常 0.55 左右），低于阈值会进「待确认字段」 |
| 合同金额抽错了（选了单价或节点款） | 跑 `--probe` 看金额候选的锚点与得分。若总价处没有「总价/总款」类词，锚点会失效 —— 这类合同建议人工填 |
| 生效/到期日期为空 | 表格版式合同常见（数字在表格里、没有「生效日期：」标签）。这类情况现在会**主动告警**：金额/日期抽不到且文本确实带表格特征时，告警里直接让你去用 `pdf-toolkit` 的 `tables` 子命令 |
| 台账里少了子目录中的合同 | v1.0.2 起子目录默认一并处理。若确认没有，先跑 `info <目录>` 看「范围」一行，并检查那些文件是否落在 `.git` / `node_modules` 之类的噪声目录里 |
| 比例合计报 105% | 检查该合同的节点是否被标成了「支付节点」而非「扣留项」。质保金/保证金若写在正文里且没有明显的扣留表述，可能被误分类 —— 看「付款节点」sheet 的原文片段 |
| `parse` 报「异常/未提取 N」 | 看「解析告警」sheet。扫描件需先 OCR，`.doc` 需先转 `.docx`，其它扩展名本技能不处理 |
| 台账里出现空行 | 那些是未提取成功的文件（状态列有值），用于保证输入与产出对得上。需要干净数据时按 `处理状态` 列筛掉 |
| 台账行数比预期多/少 | 先跑 `info <目录>`：「合计」应等于 `parse` 的「处理 N 个文件」与台账行数。**三者不等即为缺陷**，不是配置问题。注意隐藏文件与 `.git` / `node_modules` / `__pycache__` 会被排除，不计入「合计」 |
| 大量字段置信度偏低 | 说明这批合同写得比较自由。先看「待确认字段」列集中是哪些字段，再决定是人工核还是改抽取规则；有时只是阈值对本批次偏高，用 `--conf-threshold 0.55` 试一次 |
| 甲乙方认反了 | 检查是否配了我方名称。`parse` 结尾会提醒「未指定我方名称」；命中环境变量或配置文件时，输出开头会打印来源 |
